# Helm-чарт для развёртывания backend-сервисов в Kubernetes

Пример переиспользуемого Helm-чарта, применяемого в процессе деплоя backend-приложений через **GitLab CI/CD**. В нём реализованы типовые задачи эксплуатации: развёртывание приложения, запуск миграций БД, ingress-маршрутизация, проверки готовности, работа с HashiCorp Vault и диагностика ошибок деплоя.

Репозиторий содержит **обезличенный фрагмент** инфраструктурного решения. Конфигурации конкретных приложений, production-секреты и настройки доступа в CI намеренно не публикуются. Это пример для технического ознакомления, а не готовый к запуску «из коробки» проект.

## Что реализовано

- **Deployment и Service** для backend-приложения: образ, параметры запуска, запросы и лимиты ресурсов, дополнительные источники переменных окружения и тома.
- **Миграции БД** через `initContainer`: если в образе присутствует `/app/dbmigrate`, выполняется `/app/dbmigrate up`.
- Дополнительные **pre-start команды** через `initContainers`.
- Механизм дополнительных команд через контейнер Deployment и/или Helm hook `Job` (поведение и ограничения описаны ниже).
- HTTP-проверки `startupProbe`, `readinessProbe` и `livenessProbe` для `/status`.
- **NGINX Ingress**, дополнительные маршруты и опциональная настройка CORS.
- Отдельные ресурсы Deployment / Service / Ingress для страницы API-документации, включая опциональный вариант gRPC-документации.
- **Vault Secrets Operator**: шаблон `VaultStaticSecret` для синхронизации значений из HashiCorp Vault в Kubernetes Secret.
- Настройки безопасности контейнера: запрет повышения привилегий, сброс Linux capabilities и `seccompProfile: RuntimeDefault`.

## Структура репозитория

```text

```

## Деплой из GitLab CI/CD

В исходном репозитории приложения общий чарт расположен в `_charts/k8s-backend`. Деплой выполняется задачей GitLab CI/CD:

```bash
helm upgrade --install "${RELEASE_NAME}" ./_charts/k8s-backend \
  -f ./_charts/k8s-backend/values.main.yaml \
  -f values.yaml \
  "${HELM_CI_VALUES_ARGS[@]}" \
  --namespace "${DEPLOY_NAMESPACE}" \
  --create-namespace \
  --history-max 3 \
  --wait \
  --timeout 320s \
  || /usr/local/bin/check-fails "${DEPLOY_NAMESPACE}" "${RELEASE_NAME}"
```

Используются три уровня конфигурации:

1. **`values.main.yaml`** — общие настройки шаблонов.
2. **`values.yaml`** — настройки конкретного приложения из его репозитория; здесь не публикуются.
3. **`HELM_CI_VALUES_ARGS[@]`** — Bash-массив дополнительных аргументов Helm, который формируется CI-задачей из доступных ей значений в HashiCorp Vault.

Если один и тот же параметр указан несколько раз, приоритет имеют более поздние значения. Установка/обновление выполняется с ожиданием готовности поддерживаемых ресурсов до 320 секунд; Helm сохраняет не более трёх ревизий release.

### Разделение секретов CI и приложения

**Значения, необходимые CI для деплоя**, извлекаются из Vault и преобразуются в `HELM_CI_VALUES_ARGS`.

**Runtime-секреты приложения** доставляются другим путём: Vault Secrets Operator обрабатывает `VaultStaticSecret` и синхронизирует данные из Vault в Kubernetes Secret, который затем подключается контейнерами через `envFrom`. Кроме того, шаблоны ссылаются на заранее созданный общий Secret вида `<ENV_NAME>-common-secret`.

Чарт **не устанавливает** Vault Secrets Operator, его CRD, объект Vault-аутентификации, registry pull credentials и прочие общекластерные зависимости. Они должны существовать в целевом окружении.

> **Безопасность:** не следует передавать чувствительные значения непосредственно через `--set` / аргументы Helm без оценки риска: они могут попасть в список процессов, CI-логи или метаданные Helm release. Для runtime-паролей предпочтительнее ссылки на Secret, управляемые Vault Secrets Operator. Реальные `values.yaml`, токены и секреты в публичном репозитории отсутствуют.

## Локальная проверка шаблонов

Из корня этого репозитория:

```bash
helm lint . -f values.main.yaml -f values.example.yaml

helm template example-release . \
  -f values.main.yaml \
  -f values.example.yaml \
  --namespace example
```

`values.example.yaml` содержит тестовые значения и домен-заглушку. Команды показывают способ проверки шаблонов, но **не запускают работоспособное приложение**. Для реального развёртывания нужны образ приложения, доступы и настройки целевого Kubernetes-кластера.

## Диагностика неудачного деплоя

Если `helm upgrade --install` заканчивается ошибкой, CI запускает `check-fails`:

- получает список подов в namespace;
- отбирает поды, не находящиеся в состоянии `Ready`;
- выводит их статус, последние 300 строк текущих логов контейнеров и предыдущие логи (при наличии).

В GitLab Runner этот скрипт установлен как `/usr/local/bin/check-fails`; его демонстрационная копия находится в `scripts/check-fails`.

Скрипт завершается с **`exit 10`**, поэтому не скрывает ошибку Helm и не превращает неуспешный деплой в успешный pipeline.

> **Ограничение:** сейчас диагностируются все неготовые поды namespace, а не только ресурсы конкретного Helm release. Логи могут содержать чувствительные данные, поэтому доступ к результатам CI должен быть ограничен.

## Особенности и ограничения реализации

- В текущем варианте проверка `/status` и `APP_PORT` используют порт **8080**; при изменении `containerPort` проверки необходимо согласованно обновить.
- Шаблоны ссылаются на существующий image pull Secret `registry-creds` и общий Secret `<ENV_NAME>-common-secret`.
- `EXTRA_COMMANDS` создаёт дополнительный контейнер в Deployment. Если команда завершается, Kubernetes может перезапускать контейнер; для одноразовых операций правильнее использовать Job.
- При одновременном включении `JOBS` и `EXTRA_COMMANDS` одни и те же действия могут выполняться и в контейнере, и в Helm hook Job. Такой режим требует отдельной проверки, чтобы избежать повторного выполнения.
- Для дополнительных команд используется `sh -lc` и `set -euo pipefail`; shell в образе должен поддерживать `pipefail`.
- Timestamp в шаблоне pod (`now | unixEpoch`) инициирует изменение pod template при повторных обновлениях Helm.
- Это фрагмент конкретного рабочего подхода, а не универсальный готовый chart для произвольного приложения. Живой кластер и доступы в этом репозитории не предоставляются.

## О публикации

В публичной версии удалены исходное имя Vault mount и встроенные хеши паролей Basic Auth. Параметры `VAULT_MOUNT`, `SECRET_LOCATION` и при `INTERNAL=true` — `BASIC_AUTH` — передаются через values. Публикация реальных секретов или конфигураций production недопустима.
